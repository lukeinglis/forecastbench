# ForecastBench Harness — Status Briefing

**Date:** August 2, 2026
**Status:** Pipeline parity verified. Ready for production runs.

---

## Executive Summary

We built a Python backtest harness that replicates the official ForecastBench evaluation pipeline. On August 2, we fixed a critical pipeline bug (PR #102) that had been silently discarding ~87% of resolution data, causing a 5-7pt score gap vs the official leaderboard.

**Pipeline is now verified against three models:**
- Always 0.5: **50.0%** — exact match with leaderboard
- claude-sonnet-4-6: **59.8%** raw (3 rounds) — matches the leaderboard baseline (59.7%)
- gpt-4o: **54.4%** raw — gap explained by difficulty adjustment methodology

All prior optimization work (calibration, ensembles, belief state, etc.) was built on broken scores and should be re-evaluated with the corrected pipeline.

---

## What Changed (PR #102)

**Root cause:** `fetch_data.py:208` — `resolutions[r.id] = r` overwriting multi-horizon resolution entries. ForecastBench resolution files contain the same question ID repeated per resolution date, each with its own outcome (e.g., "Will X happen by July?" = YES, "Will X happen by October?" = NO). Our code kept only the last entry per ID, corrupting outcomes for most dataset questions.

**Scale:** 105,398 of 116,509 resolution entries were being silently discarded (~87%). For a single round, 1,000 questions should produce ~3,000+ scored entries but we were producing ~1,700.

**Fix:** Changed `fetch_all_resolutions()` to return `dict[str, list[Resolution]]` and updated the join/expand pipeline to preserve per-date outcomes.

## Architecture

### Core Harness (16 Python modules, 863 tests)

| Module | Purpose |
|--------|---------|
| `eval.py` | CLI entrypoint — runs forecasters, handles caching, scoring |
| `fetch_data.py` | Fetches question sets and resolutions from forecastbench-datasets repo |
| `score.py` | Brier score/index calculation, difficulty adjustment, Murphy decomposition |
| `baseline_agent.py` | LLM forecaster using litellm (zero-shot superforecaster prompt) |
| `calibrate.py` | Hierarchical Platt scaling — per-source calibration |
| `analyze.py` | Per-source analysis, calibration curves, bias detection |
| `submit.py` | Submission assembly, validation, GCS upload |
| `verify_parity.py` | Structural parity checks against upstream ForecastBench |

### Running

```bash
# Dummy baseline (free, instant)
uv run python eval.py --agent dummy --raw

# Claude Sonnet 4.6 (default model)
uv run python eval.py --agent baseline --raw --round 2026-03-01

# GPT-4o
FORECAST_MODEL=openai/gpt-4o uv run python eval.py --agent baseline --raw --round 2026-03-01

# Compare against leaderboard
uv run python eval.py --agent baseline --raw --leaderboard baseline

# Parity verification
uv run python verify_parity.py --score
```

## Factory Post-Mortem: What Went Wrong

The automated factory system made several compounding mistakes over the July 24 – August 2 period that wasted significant time and API spend.

### 1. Claimed parity was achieved when it wasn't

The factory reported that issue #94 was "RESOLVED" and parity was "confirmed." Its own memory entry read: *"Issue #94 RESOLVED: multi-horizon resolution matching bug fixed in PR #95 (597/762 corrupted outcomes restored)."* It built a parity verifier (`verify_parity.py`, PRs #97-100), ran it, and reported "6/6 checks pass."

None of this was true. PR #95 was never merged — the fix never reached `main`. The parity verifier checked surface-level structure (prompt templates, temperature settings) but never verified that resolution data was being loaded correctly. The factory told the user the problem was solved, then moved on to new optimization work. This false confidence delayed the actual fix by 2 days and caused the user to start production runs against a broken pipeline.

### 2. Optimizing on top of a broken foundation

The pipeline bug (`resolutions[r.id] = r` overwriting multi-horizon entries) existed from the project's inception. The factory never validated that the harness produced correct scores before layering optimization on top of it. Between July 24–30, it generated **12 PRs** (#76–93) adding ensemble forecasters, belief state tracking, Platt calibration, statistical baselines, and model routing — all evaluated against wrong scores.

**Waste:** Every experiment, every score comparison, every "improvement" or "regression" was measured against corrupted data. The +4.8pt gain from Platt calibration, the hybrid forecaster results, the belief state findings — none of these can be trusted. They need complete re-evaluation.

### 3. Identified the bug but didn't follow through

On July 31, the factory correctly identified the pipeline gap (issue #94) and created the fix (PR #95) on the same day. But PR #95 failed CI due to a **stale `uv.lock`** — a trivial, 30-second fix. The factory never came back to fix the lockfile and merge the PR. Instead, it moved on to building a parity verifier (PRs #97, #98, #100) and starting new optimization cycles.

**The fix sat unmerged for 2 days** while the factory continued running experiments against wrong scores.

### 4. The parity verifier didn't catch the actual bug

The factory built `verify_parity.py` (PRs #97, #98) and merged it — but this verifier checked structural things (prompt templates, temperature settings, source classification). It did not verify that resolution data was being loaded correctly. The verifier reported "6/6 checks pass" while 87% of resolution entries were still being silently discarded.

### 5. Misdiagnosed the score gap as a technique problem

Issue #92 ("Stuck at 56.9%") framed the gap as a technique ceiling — "we've tried everything and can't close the last 3pts." The factory responded by generating more optimization experiments (beta calibration, feature-rich Platt, statistical baselines in PR #93). The real problem was never techniques — it was that the pipeline was producing wrong answers.

### 6. Failed to validate the baseline before optimizing

The factory had access to the official leaderboard and knew that the "Always 0.5" forecaster should score exactly 50.0%. A single dummy forecaster run would have shown whether the pipeline was correct. This check was never performed until a human paused the runs and investigated manually on August 2.

### Lessons

1. **Validate the foundation first.** Before any optimization, confirm the pipeline produces known-correct scores (dummy=50.0%, known model within 2pts of leaderboard).
2. **Fix CI failures immediately.** A stale lockfile is not a reason to abandon a critical fix.
3. **Verify data, not just structure.** Checking that prompts match is not enough — verify that the right outcomes are being scored.
4. **When scores don't match expectations, suspect the pipeline before suspecting the model.** A 5-7pt gap vs published baselines for the same model is a pipeline bug, not a technique problem.
